# Verification and test evidence

This repository includes automated checks for the test engine, simulation behaviour, fault handling and generated reports. The project intentionally exercises both successful and unsuccessful measurements: a correctly detected fault is a **FAIL** for the device scenario, and an invalid acquisition is an **ERROR** for the measurement process.

Inspect the [example HTML](../examples/acceptance/report.html) and [JSON](../examples/acceptance/report.json) evidence. Each report contains raw measurements, configured criteria, scenario results and a SHA-256 of the test plan. The reports are ordinary artifacts, not signed or tamper-evident qualification records.

## Reproduce the results

From the repository root using Python 3.11+:

```powershell
python -m unittest discover -s tests -v
python -m validationbench --plan plans/acceptance.json --output-dir reports/acceptance
python -m validationbench --plan plans/injected_faults.json --output-dir reports/injected_faults
python -m validationbench --plan plans/recovery.json --output-dir reports/recovery
```

A non-zero exit for either diagnostic plan is intentional: it communicates the detected failures or acquisition errors to automation. The commands generate fresh reports in `reports/`, a Git-ignored directory.

## What is verified

- Parsing and validation of versioned test plans, numeric bounds, duplicate keys and unsupported fields
- Electrical limits, current and overtemperature trips, latched shutdown and thermal response in the simulation
- Per-sample acceptance criteria for voltage, current, temperature, timestamps and operating state
- Detection of injected measurement biases and incorrectly bypassed protection
- Read retry behaviour, permanent timeouts, malformed telemetry and independent cleanup attempts
- JSON/HTML serialization, HTML escaping, plan hashes and subprocess exit codes

**Scope:** These tests demonstrate the behaviour of the software and its deterministic simulated device. They do not establish calibrated electrical accuracy, real instrument compatibility, physical interlocks or production test-system suitability. The GitHub Actions workflow is configured for Windows and Linux; its status should be checked on GitHub after publication.
